## 一、Goal（任务目标）

在既有 Next.js 16 App Router + HttpOnly Cookie BFF + 统一 API Client 体系之上，实现预订运营 UI：

- 新增页面：`/reservations`、`/reservations/new`、`/reservations/[id]`、`/stays/[id]`
- 扩展页面：`/dashboard`（今日到店 / 今日离店 / 当前在住 / 未来 7 天预订）、`/rooms/[id]`（当前 Stay、实际入住时间、计划离店日期、下一笔 Reservation）
- 完整支持：Guest 搜索/创建、Availability 选择器、Check-in、Check-out、Cancel、No-show、CONFIRMED 预订编辑（改日期/房间/房型/Guest/Source/金额）
- 权限化渲染：HOUSEKEEPING 等无 `guest:read` / `reservation:read` 角色全程看不到 Guest 身份/联系方式与 Reservation 金额等数据
- Vitest 覆盖新增 UI 逻辑；基线 74 用例保持全绿

T2 结束时，前台员工可通过浏览器完成一次真实预订运营操作（与 T1 API 全链路打通）。

## 四、Business Rules（业务规则，UI 层落实）

1. **日期语义 `[check_in_date, check_out_date)`**：表单校验 `check_out > check_in`；日期选择器禁止选择退房日 ≤ 入住日；提示文案与后端一致。
2. **不可复制状态机**：前端不复制 Reservation/Stay 状态机转换表（单一事实源在后端）；非法操作直接展示后端 409 `detail`。
3. **Availability 使用**：新建预订必须先查询 Availability（真实 `GET /availability`）；无可用房间时展示 Empty 态（「所选日期无可用房间」），不允许提交。
4. **Check-in 前置**：提交 check-in 前展示房间清洁状态与日期资格（须满足 Property Business Date ∈ [check_in_date, check_out_date)，Asia/Shanghai）；后端 409（dirty / occupied / 日期未到 / 已过退房日 / 已 Check-in）原样展示为冲突提示，不得吞掉或转成通用错误。
5. **Walk-in**：新建表单 `source = WALK_IN` 时默认 `check_in_date = 今天`（今天 = Property Business Date，Asia/Shanghai；可保持其他来源逻辑一致，不设第二套流程）。
6. **金额**：展示后端返回的字符串金额（如 `"328.00"`），不自行做浮点运算展示。
7. **权限化渲染（必须，REV-02）**：
   - 无 `guest:read` 时，前端不渲染 Guest 身份/联系方式（name/phone/email/Guest notes）；无 `reservation:read` 时，不渲染 Reservation 数据（含 reservation_no、日期、房号/房型、source、status、agreed_total_amount、currency）。后端已裁剪字段，前端双保险：按权限隐藏对应区块。
   - HOUSEKEEPING 两者皆无：通过 Room Detail 只能看到房间清洁状态（dirty 可见）与「当前有客/有预订」这类非敏感摘要；看不到 Guest 身份、联系方式与预订金额。
   - 不得把 PII 写入 localStorage / console / 任何日志。
8. **错误展示**：沿用统一错误归一化（client.ts）：401 清状态跳 /login；403 渲染「无权限访问该页面」不跳登录；409 展示后端 detail；422 映射到表单字段错误（含 Room / Room Type 不一致）；网络错误显示「服务暂时不可用」+ 重新加载。
9. **CONFIRMED 预订编辑（REV-FINAL-05）**：`CONFIRMED` 状态提供完整编辑入口（Guest / Room / Room Type / 日期 / Source / 金额 / 备注）；修改日期、房间、房型前先重新查询 Availability，无可用或重叠时不允许提交（后端 409 双保险）；`CHECKED_IN` / `CANCELLED` / `NO_SHOW` / `COMPLETED` 不提供核心字段编辑。
10. **Room / Room Type 联动（REV-FINAL-06）**：选择房间自动带出其房型；手动改房型与房间不一致时提交被后端 422 拒绝并展示原因。

## 五、RBAC（权限规则）

- 前端仅改善 UI：按钮/导航/区块按 `auth/me` 权限显隐；**最终权限边界在后端**（即使前端漏隐藏，后端 403/字段裁剪兜底）。
- 权限 → UI 映射：
  - `guest:read` → 显示 Guest 身份/联系方式（name/phone/email/Guest notes）
  - `reservation:read` → 显示预订入口/列表/详情（含 reservation_no、日期、房号/房型、source、status、agreed_total_amount、currency）
  - `reservation:write` → 新建/编辑预订表单
  - `reservation:cancel` / `reservation:no_show` → 对应操作按钮
  - `stay:read` → 显示在住入口/详情
  - `stay:check_in` / `stay:check_out` → 对应操作按钮
- 无权限直接访问 URL：页面加载遇 403 → 渲染 Forbidden 视图（沿用现有模式），不跳登录、不白屏。
- HOUSEKEEPING / MAINTENANCE / FINANCE：导航不显示 预订/在住；Dashboard 不显示 PII 区块。

## 六、Data Integrity（数据完整性，UI 层）

- 所有数据来自真实 API；无假数据、无本地伪造「成功」状态。
- 提交类操作（create / cancel / no-show / check-in / check-out）完成后重新拉取详情/列表，确保展示与后端一致；刷新页面状态保持（沿用 `/rooms/[id]` 的 `key={id}` 重挂载模式）。
- 表单提交中防重复点击（禁用按钮），避免同一操作并发提交。
- 不修改任何 backend 契约；如发现 API 文档与 OpenAPI 不一致，以 OpenAPI 为准并报告。

## 七、Error Semantics（错误语义）

| 场景 | 前端表现 |
|---|---|
| 401 | 清状态跳 /login |
| 403（页面/操作） | Forbidden 视图或隐藏按钮，不跳登录 |
| 404（资源不存在） | 现有 not-found 体系 |
| 409（Double Booking / dirty / occupied / 已终态 / 已退房） | 冲突提示条 + 后端 detail 原文；表单停留可修改 |
| 422（字段校验） | 表单字段级错误 |
| 502/网络 | 「服务暂时不可用」+ 重新加载（沿用现有归一化） |

## 四、Business Rules（业务规则）

全部不可违反规则见总纲 §3，本任务逐条落实：

1. **Reservation / Stay 分离**：两个独立模型；Stay 通过 `reservation_id` 关联，一个 Reservation 最多一个 Stay。
2. **与当前房态解耦**：创建/更新未来 Reservation 不得修改 Room 的 `occupancy_status`（不得置 `reserved`）。
3. **日期区间 `[check_in_date, check_out_date)`**：`check_out_date > check_in_date`（否则 422）；紧邻允许（`9/1 → 9/3` 可与 `8/30 → 9/1` 共存）；重叠为冲突。
4. **Double Booking**：应用层预检（快速失败 + 友好报错）+ 数据库排他约束（最终仲裁）。约束定义：
   ```sql
   EXCLUDE USING gist (
     room_id WITH =,
     daterange(check_in_date, check_out_date, '[)') WITH &&
   ) WHERE (status NOT IN ('CANCELLED', 'NO_SHOW', 'COMPLETED'))
   ```
   需要 `CREATE EXTENSION IF NOT EXISTS btree_gist`（Migration 内）。排他约束只作用于仍占用日期区间的 `CONFIRMED` / `CHECKED_IN`；`CANCELLED` / `NO_SHOW` / `COMPLETED` 不再阻塞新预订（REV-01：提前退房后原 Reservation 置为 COMPLETED，释放剩余日期）。约束冲突（psycopg2 pgcode `23P01`）→ 409 + 可读 detail（如「该房间在所选日期区间已被预订」）；不得泄漏 500。
5. **权限边界（REV-02）**：`guest:read` 控制 Guest 身份/联系方式（name、phone、email、Guest notes）；`reservation:read` 控制 Reservation 数据（reservation_no、日期、房号/房型、source、status、agreed_total_amount、currency、Reservation notes）。`agreed_total_amount` **不是** Guest PII；Sprint 2 不新增 `reservation:financial_read`。无对应权限时响应模型直接裁剪字段（见「五、RBAC」）；HOUSEKEEPING 两者皆无 → 身份、联系方式、金额全部不可见。
6. **Check-in 事务**：`Reservation CONFIRMED → CHECKED_IN` + `Stay CREATE ACTIVE`（stay_no 生成、`actual_check_in_at` 默认 Property Business Date 当前时刻（Asia/Shanghai，timezone-aware）、`planned_check_out_date` = Reservation 的 `check_out_date`）+ `Room.occupancy_status → occupied` + Audit `reservation.check_in`，单事务。
   - 前置校验（事务内，REV-FINAL-01）：Reservation 存在且为 CONFIRMED；**日期资格：`business_date ∈ [check_in_date, check_out_date)`**（Property Business Date，Asia/Shanghai；未到入住日或已过计划退房日 → 409）；Room 存在且 `cleaning_status = clean`（否则 409「房间未清洁」）；Room 未被其他 ACTIVE Stay 占用。
   - 未来预订提前入住（business_date < check_in_date）→ 409；客人提前到店须先修改 Reservation 日期再 Check-in。
   - 两个并发 Check-in 同一 Reservation：一个成功，另一个 409（状态已变 / Stay 已存在）。
7. **Check-out 事务（REV-01）**：`Stay ACTIVE → CHECKED_OUT`（`actual_check_out_at` 默认 Property Business Date 当前时刻，Asia/Shanghai，timezone-aware）+ `Reservation CHECKED_IN → COMPLETED` + `Room.occupancy_status → available` + `Room.cleaning_status → dirty` + Audit `stay.check_out`（details 可含 Reservation CHECKED_IN → COMPLETED 摘要），单事务。非 ACTIVE Stay → 409。`CHECKED_IN → COMPLETED` 只能在此事务内触发，任何 Update / Action API 不得手工置为 COMPLETED。
8. **Walk-in**：不设第二套流程——`source = WALK_IN` 且 `check_in_date = today`（today = Property Business Date，Asia/Shanghai）的普通 Reservation，随后走同一 Check-in。
9. **金额**：`agreed_total_amount` 用 `Numeric(10,2)`，JSON 序列化为字符串；禁止 Float；`currency` 默认 `"CNY"`。
10. **业务单号（REV-04）**：`reservation_no` / `stay_no` 服务端生成、全局唯一（数据库 UNIQUE 约束）。**禁止 `SELECT MAX(...) + 1` 方式生成**；必须使用数据库 Sequence 或其他原子、并发安全机制（如 PG Sequence + 前缀/日期格式化）。要求：Human-readable、Unique、Concurrency-safe、Database enforced；格式由 DSH 确定（如 `RSV20260830-0001` / `STY20260830-0001`）并记录 DECISIONS。并发创建不得产生重复编号。
11. **Reservation 编辑（REV-FINAL-05）**：`CONFIRMED` 状态允许经 PATCH 修改全部主要预订信息：`guest_id`、`room_id`、`room_type_id`、`check_in_date`、`check_out_date`、`source`、`external_reference`、`agreed_total_amount`、`currency`、`notes`。修改 `room_id` / `room_type_id` / `check_in_date` / `check_out_date` 必须在同一事务内重新执行 Availability Check + Double Booking Protection（排他约束仍为最终仲裁）+ Room / Room Type 一致性校验（见规则 16）。`CHECKED_IN` / `CANCELLED` / `NO_SHOW` / `COMPLETED` 经 PATCH 修改核心业务字段 → 409。此能力是入住前预订修改（改日期/房间/房型/Guest/Source），不属于换房 / 延住工作流。
12. **Availability 规则**：按总纲 §6 实现（排除重叠 CONFIRMED/CHECKED_IN、Active Stay、blocked、out_of_service；区间含今天（Property Business Date，Asia/Shanghai）时排除当前 occupied/reserved；未来预订不要求 clean；Check-in 才要求 clean）。
13. **状态机**：按总纲 §5；非法转换 409；status 只能经专用 action 端点变更；`CHECKED_IN → COMPLETED` 仅由 Check-out 事务触发（REV-01）；`CONFIRMED → CHECKED_IN` 需日期资格（REV-FINAL-01）；`CONFIRMED → NO_SHOW` 需 `business_date >= check_in_date`（REV-FINAL-02）。
14. **不存储**任何身份证号/照片/人脸/公安数据（模型层就不存在这些字段）。
15. **created_by / updated_by**：FK → users.id（nullable，ON DELETE SET NULL，沿用 audit_logs.user_id 模式），由当前认证用户填充。
16. **Room / Room Type 一致性（REV-FINAL-06）**：`reservation.room_type_id` 必须等于 `room.room_type_id`。创建时校验；PATCH 修改 `room_id` / `room_type_id` 时重新校验。不一致 → 422（输入组合不合法；若 DSH 判断 409 与现有错误语义更一致，必须在 DECISIONS.md 记录原因）。
17. **No-show 日期资格（REV-FINAL-02）**：仅 `CONFIRMED` 且 `business_date >= check_in_date` 时可执行 `CONFIRMED → NO_SHOW`；未来预订（business_date < check_in_date）→ 409。
18. **时间戳**：`actual_check_in_at` / `actual_check_out_at` / `created_at` / `updated_at` 一律 timezone-aware（Asia/Shanghai）；业务日期判断统一使用 Property Business Date；禁止依赖宿主机本地时区。

- **权限裁剪（后端实现，必须，REV-02）**：无 `guest:read` 时，以下出口不得出现 Guest 身份/联系方式 `name / phone / email / Guest notes`（含嵌套）；无 `reservation:read` 时不得出现 Reservation 数据（`reservation_no`、日期、房号/房型、source、status、`agreed_total_amount`、currency、Reservation notes）：
  - `GET /guests*`（整体 403，根本不返回）
  - `GET /reservations*`、`GET /stays*` 中的 guest 关联信息：无 `guest:read` 时仅保留 `guest_id`（供关系关联），**不得返回 `guest_name` / `name` / `phone` / `email` / Guest `notes`**（REV-FINAL-04）
  - `GET /rooms/{id}` 扩展后的 current_stay / next_reservation 摘要
  - Dashboard 汇总（T2 消费）
  - Audit Log details（见「八、Audit Log」）
  - 任何 Network Response
- 实现方式：响应模型按权限动态裁剪（例如 serializer 根据 `guest:read` / `reservation:read` 决定是否填充敏感字段），前端隐藏不算数。HOUSEKEEPING 两者皆无 → 身份、联系方式、金额全部不可见；Room Detail 最多只能看到 `has_active_stay = true`（当前有客）类非身份摘要，绝不出现 guest_name / 手机号 / email / 金额 / Reservation 详情（REV-FINAL-04）。

## 六、Data Integrity（数据完整性）

1. **Migration**（一个 revision，可 down）：`CREATE EXTENSION IF NOT EXISTS btree_gist`；`reservation_status`（CONFIRMED/CANCELLED/NO_SHOW/CHECKED_IN/**COMPLETED**，REV-01）/ `stay_status` PG 枚举；`guests` / `reservations` / `stays` 表；外键（guest_id、room_id、room_type_id、reservation_id、created_by/updated_by → users.id nullable SET NULL）；唯一约束（`reservation_no`、`stay_no`、`stays.reservation_id`）；排他约束（见 Business Rules 4）；业务单号使用数据库 Sequence 原子生成（REV-04，禁止 SELECT MAX+1）；必要索引（room_id + check_in_date/check_out_date、status、guest_id、日期重叠查询）。
2. **事务边界**：Reservation 创建与 PATCH 修改（含排他约束冲突捕获与重新校验）、Check-in、Check-out、Cancel、No-show 均在同一事务内完成，含审计写入；失败全回滚。
3. **并发安全**：排他约束为最终仲裁；`stays.reservation_id` 唯一约束防重复入住；应用层状态校验防已 Check-in 重复操作。
4. **金额**：Numeric；所有序列化走字符串。
5. **种子**：新增权限/角色映射幂等；重复执行收敛；不覆盖既有 17 权限语义。
6. **禁止**：直接改表绕过 Migration；生产库直改（只允许 dev 库经 alembic、测试库经 conftest/prepare 脚本）。

## 七、Error Semantics（错误语义）

沿用总纲 §11。本任务落实：

| 场景 | 状态码 | 说明 |
|---|---|---|
| 未认证 / Token 失效 | 401 | 沿用现有 |
| 无权限（含无 guest:read 请求 PII） | 403 | 沿用现有 |
| 资源不存在 | 404 | guest/reservation/stay/room 不存在 |
| Double Booking（含并发撞约束） | 409 | detail 可读（如「该房间在所选日期区间已被预订」） |
| Room unavailable（blocked/out_of_service/重叠） | 409 | 创建预订或查询时按规则 |
| Dirty room Check-in | 409 | 「房间未清洁，请先安排保洁」类文案 |
| Occupied room Check-in | 409 | |
| Check-in 日期资格不符（business_date < check_in_date 或 >= check_out_date） | 409 | REV-FINAL-01 |
| 未来预订 No-show（business_date < check_in_date） | 409 | REV-FINAL-02 |
| Cancelled / NO_SHOW Reservation 后续操作 | 409 | cancel/no-show/check-in 对已终态记录 |
| 已 Check-in Reservation 再次 Check-in | 409 | |
| Already Checked-out Stay | 409 | 再次 check-out |
| 非法状态机转换 | 409 | 沿用状态机统一出口 |
| 非 CONFIRMED 状态 PATCH 核心字段 | 409 | 见 Business Rules 11（REV-FINAL-05） |
| Room / Room Type 不一致 | 422 | 或 409（须记录 DECISIONS，REV-FINAL-06） |
| 日期非法（co <= ci、格式错） | 422 | 输入验证 |

错误格式沿用 `{"detail": "..."}`；排他约束异常必须捕获映射为 409，不得 500。

```text
Business number concurrency（并发创建多个 Reservation / Stay → reservation_no / stay_no 无重复、唯一约束生效；
           实现禁止 SELECT MAX+1，必须使用数据库 Sequence，REV-04）
Reservation PATCH 编辑（CONFIRMED 修改日期/房间 → Availability 重新检查；修改后 overlap → 409；
           CHECKED_IN/CANCELLED/NO_SHOW/COMPLETED 修改核心字段 → 409，REV-FINAL-05）
Room / Room Type 一致性（创建 mismatch → rejected；有效组合 → success；PATCH 后 mismatch → rejected，REV-FINAL-06）
Query contract（GET /guests search=name/phone；GET /reservations 各筛选 + search（reservation_no / Guest name/phone，
           遵守 guest:read）；GET /stays 各筛选；今日到店/今日离店/当前在住/未来 7 天 = 既有 List API 组合，REV-FINAL-07）
```

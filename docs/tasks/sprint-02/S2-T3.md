## 四、Business Rules（业务规则，E2E 落实）

1. **真实链路**：E2E 只经浏览器 + BFF + 真实 FastAPI（127.0.0.1:8001）+ 独立 `stayops_test` 库；禁止任何 Mock/Stub 冒充成功。
2. **动态日期（REV-FINAL-03）**：所有 E2E 日期基于 Property Business Date（Asia/Shanghai，`business_date`，禁止依赖宿主机本地时区）生成。Golden Path / Early Checkout 使用 `check_in_date = today`、`check_out_date = today + 2`，当天创建、当天入住、当天退房（测试执行时系统日期不会自动前进，故不得使用 today+N 入住）。文档中的 2026-08-30 → 2026-09-01 仅为业务故事示例，不得用于固定自动化测试。
3. **Golden Path 剧情**（与总纲 §2 对应；自动化日期 = today / today+2）：前台（FRONT_DESK 账号）→ 创建 Guest「张先生」→ 查询 Availability（目标房可用）→ 创建预订（房 203、`[today, today+2)`、source = WECHAT）→ 第二个重叠预订 `[today, today+2)` → 409 → **当天**入住（Reservation CHECKED_IN、Stay ACTIVE、203 occupied）→ **当天**退房（Stay CHECKED_OUT、Reservation **COMPLETED**、203 available + dirty）→ 审计日志完整（admin 查看）。
4. **Early Checkout（REV-FINAL-03）**：专项用例——Reservation A = `[today, today+2)`，**当天**入住 → Stay ACTIVE、Reservation CHECKED_IN；**当天**提前退房 → Stay CHECKED_OUT、Reservation **COMPLETED**、Room available + dirty；随后同一 Room 创建 Reservation B = `[today+1, today+3)` 必须成功。该用例同时证明：若 A 未正确进入 COMPLETED，`[today, today+2)` 与 `[today+1, today+3)` 重叠必然触发 409；只有 COMPLETED 正确释放剩余日期后 B 才能成功。
5. **权限断言（REV-02 / REV-FINAL-04）**：HOUSEKEEPING 登录后：能见 203 `dirty`；页面无 Guest 身份/联系方式（name/phone/email/Guest notes，含 guest_name）与 Reservation 数据（含 agreed_total_amount）；直接请求 guests/reservations/stays API → 403；网络响应体（Playwright 拦截断言）不含上述字段；Room Detail 仅见 `has_active_stay` 类非身份摘要。
6. **并发断言（REV-FINAL-08）**：两个并发 `POST /reservations`（同一房、重叠区间）→ 恰好一个成功 + 一个 409；数据库最终恰一条。两个并发 Check-in 同一 Reservation → 一个成功 + 一个 409。两个并发 `POST /stays/{id}/check-out`（同一 ACTIVE Stay）→ 一个成功 + 一个 409；最终一致状态：Stay=CHECKED_OUT、Reservation=COMPLETED、Room=available+dirty；无重复审计 / 无 500 / 无部分状态 / Room 状态不反复变化。
7. **失败断言**：dirty 房入住 → 409 且 UI 显示后端 detail；未来入住日预订（如 `[today+1, today+3)`）今天 check-in → 409（日期未到，REV-FINAL-01）；未来预订 no-show → 409（REV-FINAL-02）；已退房 Stay 再退房 → 409；CANCELLED 预订再操作 → 409。
8. **隔离纪律**：pytest 与 E2E 不得并行（沿用现有互斥规则）；单 worker 串行；测试库由既有 `prepare_test_db.py` 每次全新引导。

## 五、RBAC（权限规则，E2E 覆盖）

- 账号矩阵（幂等创建，沿用 `setup-users.ts` 模式）：SUPER_ADMIN（admin）、FRONT_DESK、HOUSEKEEPING；如 T3 需要 MANAGER 可幂等补充。
- 断言：FRONT_DESK 见 预订/在住 导航并可完成 Golden Path；HOUSEKEEPING 不见预订入口、直连 403、无 PII；admin 可见审计全链路。
- 前端隐藏 + 后端 403 + 响应字段裁剪三层全部验证。

## 六、Data Integrity（数据完整性，E2E 落实）

- 每次运行从干净测试库开始（DROP/CREATE → `alembic upgrade head` → 幂等 seed，沿用既有脚本）；不触碰 dev 数据（8000/3000）。
- 用例间数据依赖显式构造、幂等清理（或依赖单 worker 串行 + 独立库的确定性）。
- 关键中间态断言：入住后 Room 占用状态、退房后 `available + dirty`、Stay 数量恰 1、审计事件齐全。

## 七、Error Semantics（错误语义，E2E 断言）

- 409 场景：Double Booking、dirty check-in、occupied check-in、已终态操作、已退房 check-out —— 状态码与 UI 文案双断言。
- 403：HOUSEKEEPING 直连预订 API；UI Forbidden 视图（不跳登录）。
- 401：未登录访问受保护页 → 跳 /login。
- 404：不存在资源（如 `/reservations/999999`）→ 页面/接口 404 语义正确。

## 八、Audit Log（审计，E2E 验证）

- Golden Path 完成后以 admin 打开 `/settings/audit-logs`，断言存在：`guest.create`、`reservation.create`、`reservation.check_in`、`stay.check_out`（以及按剧情产生的 cancel/update/no_show 若执行）。
- 审计 details 断言不含完整手机号/邮箱/notes/金额。
